# 追问智能体改造方案

> 目标：把面试提交流程从"答完 → 固定取下一题"升级为"答完 → 智能体自主决策（追问 or 放行）"，
> 让"多智能体协同"从规划变成已实现，形成"观察 → 决策 → 行动 → 评估"的完整智能体闭环。

---

## 一、为什么做（答辩价值）

现状是 1对1 单轮固定问答流：出题 → 答题 → 顺序取下一题，没有真正的追问。
追问智能体是整个项目里**智能体三要素（自主决策 / 感知上下文 / 使用工具）第一次全部落地**的模块：

| 答辩问题 | 回答 |
| --- | --- |
| 智能体体现在哪 | 提交回答后，LLM 自主判断"回答是否需要深挖"，这个分支不是代码写死的 if，是模型当场决策 |
| 和普通调大模型的区别 | 普通调用=你问它答；这里给它上下文和规则，它输出结构化行动指令（followup/next），代码只执行决策 |
| 未来怎么扩展 | 评估智能体、润色智能体（规划中）→ 多智能体协同；弱项数据作为感知上下文注入 |

## 二、技术选型结论（已论证，零新增依赖）

| 技术 | 结论 | 一句话理由 |
| --- | --- | --- |
| LangChain / LangGraph | 不用 | 单 Agent 单步决策，openai SDK 一次调用 + JSON 解析即可，框架的编排能力用不上 |
| MCP | 不用 | 工具是同进程内函数调用（查题、查回答），无跨应用复用需求 |
| 知识图谱 / Neo4j | 不用 | 上下文是"题目+回答+简历文本"，SQL 直查拼 prompt 即可，无多跳关系查询 |
| 向量 RAG（Milvus 等） | 不用（思想已用） | 简历/历史数据"少且小"，全文注入优于向量检索；未来题库上千道再评估 |

最终技术栈：**qwen-flash（复用 `LLM_MODEL`）+ `call_llm_api` / `_parse_json_content`（question_service.py 已有的两个工具函数）+ 进程内 SQL 取上下文**。requirements.txt 不加任何包。

## 三、现状流程与接入点（关键发现）

`app/api/interview_api.py` 的 `submit_text_answer`（L227-305）现在的流程：

```
UPDATE 回答到当前题
    ↓
SELECT 下一题:  WHERE interview_id=? AND id > 当前题id  ORDER BY id ASC LIMIT 1
    ↓
全答完 → status=3；返回 next_question 给前端
```

**关键发现**：下一题按 `id > 当前题id` 顺序取。所以在 UPDATE 之后、SELECT 之前**插入一条追问题**（自增 id 必然更大），追问会自然被 SELECT 命中、作为"下一题"返回前端——

**结论：前端取题逻辑、get_question 接口、面试状态流转、配额扣减，全部零改动。**

接入点示意：

```python
# submit_text_answer 内，L252 UPDATE 之后、L255 SELECT 下一题之前：
# 【追问智能体】观察本次回答，自主决定是否插入追问题
decision = decide_followup(conn, interview['id'], question_id, answer_text)
# decision == None（放行/调用失败）→ 什么都不做，走原流程
# decision == {"question": "...", "score_standard": "..."} → 插入追问题，自动成为下一题
```

## 四、智能体设计

### 4.1 决策函数（新建 `app/ai_services/followup_service.py`）

```python
def decide_followup(conn, interview_id, question_id, answer_text):
    """追问决策智能体：观察回答 → 自主决定 追问 / 放行

    返回:
        None                      → 放行（或任何失败场景的兜底，主流程照常）
        {"question": 追问文本,
         "score_standard": 评分标准} → 需要追问，调用方负责 INSERT
    """
```

流程：

1. **代码硬闸（先于 LLM，防死循环 + 省调用费）**：
   - 当前题本身是追问题（`question_type='followup'`）→ 放行（每题最多追问 1 次）
   - 本场追问数 ≥ 3（`COUNT(*) WHERE interview_id=? AND question_type='followup'`）→ 放行
   - 回答文本 < 30 字 → 直接追问规则不适用？不，交给 LLM（过短回答恰恰最该追问）
2. **感知上下文拼装（全部进程内 SQL，即智能体的"工具"）**：
   - 当前题目文本、面试类型名（interview_types.name）
   - 本次回答全文（截断 1500 字防爆上下文）
   - 本场已问题目列表（防追问重复话题）
3. **一次 LLM 调用**：system prompt 给角色与决策规则，要求输出 JSON
4. **解析与兜底**：`_parse_json_content` 解析失败 / 调用异常 / action 不是 followup → 一律返回 None（放行），**绝不卡死主流程**

### 4.2 决策 Prompt 草案

```
你是一名经验丰富的面试官，正在评估候选人刚提交的回答，决定是否需要追问。

【面试类型】{interview_type_name}
【当前题目】{question_text}
【候选人回答】{answer_text}
【本场已问过的问题】{asked_questions}

决策规则（按优先级）：
1. 回答含糊、缺少具体细节（如只说"做了优化"没说怎么做）→ 追问，挖具体做法/数据
2. 回答与题目明显跑偏 → 追问拉回主题
3. 回答自相矛盾或可疑（项目存疑、数据夸大）→ 追问验证真实性
4. 回答完整、具体、切题 → 放行（action=next）
5. 每个问题最多追问一次（你看到的回答如果是针对追问的，一律放行——代码已保证此时不会调用你）

追问要求：
- 只有一个问题，口语化、自然，像真人面试官的口吻
- 不得与【本场已问过的问题】重复
- 长度不超过 60 字

严格输出 JSON（不要输出其他内容）：
需要追问：{"action": "followup", "text": "追问内容", "score_standard": "这条追问考察什么、好的回答长什么样（50字内）"}
放行：    {"action": "next"}
```

### 4.3 三要素对照（答辩口径）

| 智能体要素 | 本实现中的体现 |
| --- | --- |
| 自主决策 | followup / next 的分支由 LLM 输出的 JSON 决定，不是代码写死 |
| 感知上下文 | 输入含题目、回答全文、面试类型、已问列表，全部实时从库里感知 |
| 使用工具 | 查题、查回答、统计追问次数——进程内 SQL 函数（无需 MCP，见选型结论） |

## 五、改造步骤（按顺序执行）

### 步骤 1：新建 `app/ai_services/followup_service.py`（核心，约 120 行）

- `decide_followup(conn, interview_id, question_id, answer_text)` 主函数
- 复用 `question_service.py` 的 `call_llm_api` + `_parse_json_content`（import 即可，不复制代码）
- INSERT 追问题**不由本函数做**（只返回决策结果，写库交给 API 层）——职责分离：智能体只决策，代码管执行

### 步骤 2：`app/api/interview_api.py` 接线（约 +15 行）

位置：`submit_text_answer` 的 UPDATE（L248-252）之后、SELECT 下一题（L255）之前。

```python
# 【追问智能体】观察回答，自主决定是否插入追问题
try:
    decision = decide_followup(conn, interview['id'], question_id, answer_text)
except Exception as e:
    logger.error(f"[Followup] 决策失败（放行兜底）: {e}")
    decision = None

if decision:
    # 追问语音预生成：失败不阻断（与主出题同一模式，见 save_questions_to_db）
    audio_data, _ = synthesize_speech(decision["question"], voice_type_of_this_interview)
    conn.execute('''
        INSERT INTO interview_questions
        (interview_id, question, score_standard, question_type, question_audio, voice_type)
        VALUES (%s, %s, %s, 'followup', %s, %s)
    ''', (interview['id'], decision["question"], decision["score_standard"],
          audio_data, voice_type_of_this_interview))
    conn.commit()
# 之后原样执行 SELECT 下一题：追问题 id 更大，自动被取到、返回前端
```

注意：`voice_type` 从 `interviews` 表取（SELECT 时顺带查出，与出题链路同源）。

### 步骤 3：前端 `app/static/interview.html` 追问标签（约 +10 行）

- 展示题目时判断 `next_question.question_type === 'followup'` → 题目卡片加小徽标「追问」，样式复用现有标签风格
- 其余交互（录音、提交、下一题）完全不变

### 步骤 4：报告闭环（约 +3 行）

`report_service.py` 生成报告的 prompt 里加一句：若本场存在 `question_type='followup'` 的题，提示模型"本次面试包含追问环节，请结合候选人面对追问的表现进行评估"。问答数据本身已自动进报告（按 interview_id 全量拉取，零改动）。

### 步骤 5：README 更新

- 功能特点加"追问智能体"一条；面试流程图加追问分支；API 表无需新增端点（复用 submit/get_question）

## 六、数据库与配额影响

| 项 | 影响 |
| --- | --- |
| 表结构 | **零改动**（复用 interview_questions，question_type 存 `'followup'` 标记；原字段存的是题目分类，互不冲突） |
| 配额 | **不扣**（配额在开始面试"大模型成功出题"时扣 1 次，追问发生在面试中途，天然不触发） |
| 状态流转 | 零改动（"全部答完"的统计自动把追问题算进去：追问必须回答完面试才算完成，符合预期） |
| 面试时长 | 每次追问给候选人加一题，question_count 统计口径不变（总题数动态 +1） |

## 七、兜底与边界设计（稳定性优先）

| 风险 | 兜底 |
| --- | --- |
| LLM 调用失败 / 超时 | decide_followup 内部捕获 → 返回 None → 主流程照常（与语音转写兜底同一思路） |
| JSON 解析失败 / 格式不符 | `_parse_json_content` 失败 → 放行 |
| 无限追问死循环 | 双保险：代码硬闸（每题 1 次 + 每场 3 次）+ prompt 规则第 5 条 |
| 追问 TTS 失败 | 只记日志继续入库（与 save_questions_to_db 模式一致，前端有浏览器 TTS 兜底） |
| 提交接口延迟 | 追问决策增加 1~3 秒（qwen-flash），前端提交本就有 loading；可接受，暂不优化 |
| 回答为空/极短 | 不做代码拦截，交给 LLM 判断（极短回答大概率触发追问，这正是期望行为） |

## 八、测试计划

| 用例 | 预期 |
| --- | --- |
| 正常完整回答（如条理清晰的项目介绍） | action=next，流程无感知 |
| 含糊回答（"就是做了个优化，效果挺好"） | 插入追问题，前端显示追问徽标，答题后继续 |
| 对追问的回答 | 不再二次追问（硬闸），正常进入下一题 |
| 同场连答多题 | 追问总数 ≤ 3 |
| 把 LLM_MODEL 改成无效值再提交 | 决策失败静默放行，提交接口正常返回 200 |
| 最后一题触发追问 | 追问答完后 status 才变 3，报告正常生成且包含追问 |
| 全程对比配额 | 追问前后 users.interview_quota 数值不变 |

## 十、未来规划（答辩"演进方向"素材，非本期实现）

1. **弱项定向出题**（RAG 变体）：报告生成时聚合各题得分 → `practice_progress` 记录弱项类型 → 下次同类型面试出题 prompt 注入弱项上下文，提高弱项题占比

3. **向量 RAG 场景**：题库上千道后做语义查重/相似题推荐；支持企业上传岗位知识库文档
4. **追问工具增强**：给智能体加"查简历原文"工具验证项目真实性（需要时再做，当前简历摘要已在上下文中）
