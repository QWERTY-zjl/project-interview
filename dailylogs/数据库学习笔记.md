# 数据库学习笔记：SQLite / ER 图 / 连接池 / 工具

> 数据库主题参考笔记，涵盖数据库本体、表结构设计、连接管理与工具生态

## 一、SQLite

### 1.1 是什么

**嵌入式单文件数据库**：没有服务端进程，整个数据库就是一个文件，程序直接读写这个文件。Python 标准库 `sqlite3` 零配置可用。

### 1.2 对比 MySQL

| | SQLite | MySQL |
|---|---|---|
| 架构 | 无服务端，直接操作文件 | 客户端-服务端 |
| 并发管理 | 文件锁，粗粒度 | 服务端调度（行级锁、MVCC） |
| 连接方式 | 打开文件即可（无主机/端口/密码） | 需要地址、账号密码 |
| 适合 | 单机、学习、小工具、移动端 | 多人访问的 Web 服务 |

两者同为关系型数据库、都用 SQL，但**没有亲缘关系**，只是定位不同。

### 1.3 并发与锁

```
多进程同时读：  ✅ 可以（共享读锁）
写：            ⚠️ 全库独占 —— 同一时刻要么"多个读者"，要么"一个写者"
```

- 报错 `database is locked` = 有别的连接占着写锁/挂着事务，默认等 5 秒超时
- 排查思路：检查还有哪些程序开着这个库（GUI 工具、后端服务），关掉再试
- 升级方案：`PRAGMA journal_mode=WAL;` 让"读写不互斥"，执行一次持久生效

### 1.4 元数据与表结构

- 每个库自带"目录表" `sqlite_master`，存着所有表的定义：`SELECT type, sql FROM sqlite_master`
- GUI 工具的"定义/DDL"标签、自动 ER 图，底层就是查这些元数据画出来的
- SQLite **默认不强制外键约束**：建表语句里写 FOREIGN KEY 主要用于文档说明和工具画线，数据一致性靠应用层保证

## 二、ER 图（实体-关系图）

### 2.1 是什么

ER 图（Entity-Relationship Diagram）用来描述数据库设计：有哪些**表**（实体）、每张表有哪些**字段**（属性）、表和表之间怎么**关联**（关系）。是设计数据库和读懂他人设计的通用语言。

### 2.2 方块 = 表

```
users {
    INTEGER id PK      ← 主键（Primary Key）：这张表的"身份证号"，唯一不重复
    INTEGER user_id FK ← 外键（Foreign Key）：存的是别的表的主键，用来"指向"那张表
    TEXT username      ← 普通字段
}
```

读表诀窍：**先找 PK（我是谁），再找 FK（我属于谁）**——表与表的连线就落在 FK 字段上。

### 2.3 连线 = 关系（鸦爪记号 Crow's Foot）

```
users ||--o{ interviews : "user_id"
读作：一个用户可以有 0~N 场面试；每场面试必须属于恰好 1 个用户
```

| 符号 | 含义 | 渲染后长什么样 |
|---|---|---|
| `\|\|` | 恰好 1 个 | 两横杠，像"=" |
| `o{` | 0 到 N 个 | 圆圈 + 鸦爪（三叉） |
| `\|{` | 1 到 N 个 | 鸦爪（无圆圈） |
| `o\|` | 0 或 1 个 | 圆圈 + 横杠 |

口诀：**数横杠定"一"，看分叉定"多"，见圆圈加"可以没有"**；连线上的标签 = 关联用的外键字段名。

### 2.4 读图三步法

1. 找**没有 FK 的"根表"**（通常是 users、分类表这类基础数据）
2. 看 **FK 最多的表**（往往是业务枢纽，如订单、记录表）
3. 顺着每条线**念成中文句子**，用业务常识检验合理性

常见结构：漏斗收窄（宏观 → 细节）；一张表有多个 FK = 同时属于多个维度（交叉记录）。

### 2.5 画图工具对比

| 工具 | 方式 | 适用场景 |
|---|---|---|
| Navicat / DBeaver「逆向数据库到模型」 | 连上真库自动生成 | 看现有库的结构（最常用） |
| Mermaid | 纯文本写在 Markdown 里 | 文档/README，git 能 diff，AI 好生成 |
| draw.io | 手动画，存文件 | 架构图、自由排版 |
| PowerDesigner / PDManer | 正式设计文档 | 传统企业（银行、国企） |

### 2.6 求职视角

能力层次：**ER 设计思想 > 读图能力 > 某个工具的语法**。面试考的是"给一个业务场景设计几张表、什么关系"，白板画鸦爪记号是通用语言；Mermaid 只是载体，会读会改即可。

## 三、数据库连接管理与连接池
当你建立起一个数据库和软件配套运行时，软件在明面上运行，数据库在背地里修改，他们并行不悖是依靠什么呢？答案是连接。
### 什么是连接？
**连接**（Connection）是指软件与数据库之间的通信通道，用于执行 SQL 语句和接收结果。就是软件修改了某个信息时，软件会通过连接向数据库发送 SQL 语句，数据库会执行语句修改数据库种相应的表。
### 是谁在申请连接？
不是软件不是用户而是代码执行到某个数据库操作时执行的，所以申请连接的是一个操作，每次修改数据库时都需要申请一个连接，该对象类似于文件的句柄——拿到它才能对数据库执行 SQL，连接关闭后就无法再操作了。
### 连接管理
你的软件给很多人在用，那么数据库的连接并修改就会很频繁，对连接的管理至关重要，连接管理包括连接的创建、维护、关闭等操作。
### 最朴素的做法
```
"""数据库模块

作用：整个项目所有需要读写 SQLite 数据库的代码，都通过这里拿连接/还连接。
相当于数据库的「统一入口」，其他模块不直接 import sqlite3。
"""

import os
import sqlite3          # Python 自带的 SQLite 驱动，标准库，不用安装
import logging
from app.config.config import DATABASE_NAME  # 从配置文件读取数据库文件路径

# logging.getLogger(__name__)：拿到本模块专属的日志记录器，
# 打日志时会自动带上模块名（如 app.db.db），方便排查是哪个文件输出的
logger = logging.getLogger(__name__)

# 全局连接池，用于管理所有活跃的数据库连接
# 本质就是一个普通 Python 列表，记录当前「借出去还没还」的连接对象。
# 作用：程序退出时能统一关闭所有连接，避免数据库文件被占用。
# 注意：SQLite 本身不支持真正的多线程连接池，这里只是简易登记。
_connections = []

def get_db():
    """获取数据库连接

    谁要用数据库，谁就调这个函数「借」一个连接。
    用完后必须调 return_db(conn) 还回去。

    Returns:
        sqlite3.Connection: 配置了行工厂的数据库连接对象
    """
    # 连接数据库文件（DATABASE_NAME 是配置里的路径，如 app/db/interview_system.db）。
    # 如果文件不存在，SQLite 会自动创建一个空的 .db 文件
    conn = sqlite3.connect(DATABASE_NAME)
    # row_factory = sqlite3.Row：设置「行工厂」。
    # 默认查出来的每行是元组 (值1, 值2)，只能按下标取 row[0]；
    # 换成 Row 后可以像字典一样用列名取：row["user_id"]、row.keys()。
    # 这是本项目所有查询都能写 row["列名"] 的原因
    conn.row_factory = sqlite3.Row  # 支持列名访问
    # 登记到全局列表，表示这个连接已借出、尚未关闭
    _connections.append(conn)
    return conn

def return_db(conn):
    """关闭数据库连接并从连接池移除

    「还连接」：用完必须关掉，否则连接一直占着数据库文件（Windows 上
    表现为 .db 文件被锁定，其他工具打开会报 database is locked）。

    Args:
        conn: 数据库连接对象
    """
    # 两个判断：conn 不是 None，且确实是之前借出去的（在列表里登记过），
    # 防止重复关闭或关掉别人的连接
    if conn and conn in _connections:
        conn.close()            # 真正关闭与数据库文件的连接
        _connections.remove(conn)  # 从登记列表中移除

def init_db():
    """初始化数据库（创建表结构）

    程序启动时调用一次。不管数据库文件存不存在，都交给
    create_personal_interview_system_db.py 处理（该脚本内部会
    判断文件是否存在，然后建库建表或补齐缺失的字段/表）。
    两个分支 import 同一个模块，是因为建表脚本里两种情况都覆盖了。
    """
    if not os.path.exists(DATABASE_NAME):
        # 数据库不存在，创建新数据库
        import app.create_personal_interview_system_db
    else:
        # 数据库已存在，更新表结构（比如以前没这个字段的表补上字段）
        import app.create_personal_interview_system_db

def close_all_connections():
    """关闭所有数据库连接（程序退出时调用）"""
    # _connections[:] 是浅拷贝：先复制一份再遍历删除。
    # 如果直接遍历 _connections 边遍历边 remove，列表长度变化会导致
    # 漏删或跳过元素，这是 Python 列表遍历删除的经典坑。
    for conn in _connections[:]:  # 使用副本避免迭代时修改
        try:
            conn.close()
            _connections.remove(conn)
        except Exception as e:
            # 单个连接关闭失败只记日志，不影响其他连接继续关闭
            logger.error(f"[DB] 关闭连接失败: {e}")

```
注意：这里的列表**只是登记簿，不是池子**——`get_db()` 每次都是**新建**一个连接并登记，`return_db()` 直接关闭并移除，连接不复用。列表的真正用途只有一个：程序退出时能按名单统一关闭所有还开着的连接。真正的复用式连接池见下一节 db_pool.py。

### 连接池
最朴素的做法每次建立连接关闭连接都是需要耗时的，本地项目还好，一旦项目是真实上线的，访问的不是本地数据库文件了，就涉及网络传播的问题（建立TCP 连接 + 密码认证防止网络传输泄密 + ），延时会大大增加，于是就有了连接池的概念。
### 什么是连接池？
可以理解为**缓存**——缓存的对象不是数据，而是“连接”本身：程序启动时预先建立好一批连接放进池子，要用就借、用完就还，连接在池子里反复复用，而不是反复新建/销毁。目的是省掉每次建立、断开连接的固定开销（“建连税”）。

对 SQLite 这种本地文件库，建连只是打开一个文件，开销很小；一旦换成 MySQL 等网络数据库，每次建连要 TCP 握手 + 密码认证，毫秒级开销 × 高并发访问，连接池就从“可选”变成“标配”。
### 与最朴素的做法的区别

| | 朴素做法（db.py） | 连接池（db_pool.py） |
|---|---|---|
| 借连接 | 每次新建一个 | 从池里 `pop()` 取现成的 |
| 还连接 | `close()` 直接关闭 | `append()` 放回池子复用 |
| 列表/池里存什么 | 借出去还没还的（登记用途） | 空闲可借的连接 |
| 池空时 | 无所谓，总能新建 | 本实现返回 None；真池子会排队等待 |
| 适用场景 | SQLite 本地文件（建连便宜） | MySQL 等网络库（建连贵，高并发必配） |

> 补充：两种方案二选一即可，不需要同时用。pool_size 限制的是“同一时刻最多多少个数据库操作在执行”，不是用户数——用户绝大部分时间在“看”而非“写库”，10 个连接服务几百个在线用户没问题。

### 实现
```
"""
数据库连接池模块
================
本模块负责管理数据库连接池，提高数据库操作性能

和 db.py 的区别：
- db.py 的 _connections 只是「登记表」，每次 get_db 都新建连接、return_db 直接关闭
- 这里是「真池子」：启动时预建好 N 个连接，用完归还而不是关闭，
  下次借就直接拿，省去了反复建立/断开连接的开销（复用思想）
"""

import sqlite3
from sqlite3 import Connection          # 连接对象的类型，只用于类型注解
from typing import List, Optional
from app.config.config import DATABASE_NAME


class DatabasePool:
    """
    数据库连接池类
    """
    
    def __init__(self, db_name: str, pool_size: int = 5):
        """
        初始化数据库连接池
        
        参数:
            db_name: 数据库文件名
            pool_size: 连接池大小（预先建好多少个连接，默认 5 个）
        """
        self.db_name = db_name
        self.pool_size = pool_size
        self.pool: List[Connection] = []   # 池子本体：一个装连接的列表
        self._initialize_pool()            # 下划线开头 = 内部方法，建议外部不直接调用
    
    def _initialize_pool(self):
        """
        初始化连接池

        一口气建好 pool_size 个连接放进池子，之后所有使用者都从池里借。
        """
        for _ in range(self.pool_size):    # _ 表示循环变量用不到，只为循环指定次数
            conn = sqlite3.connect(self.db_name)
            conn.row_factory = sqlite3.Row  # 同 db.py：让查询结果支持按列名取值
            self.pool.append(conn)
    
    def get_connection(self) -> Optional[Connection]:
        """
        从连接池获取连接
        
        返回:
            数据库连接对象，如果连接池为空则返回None

        pop() 从列表末尾取出并移除（O(1)）——「借出」一个连接。
        池空时返回 None 而不是报错，调用方需自己判空。
        """
        if self.pool:
            return self.pool.pop()
        return None
    
    def return_connection(self, conn: Connection):
        """
        将连接返回连接池
        
        参数:
            conn: 数据库连接对象

        归还而不是关闭——这是和 db.py 的 return_db 最大的区别。
        if 判断防止把同一个连接重复还两次（池里出现重复连接）。
        """
        if conn and conn not in self.pool:
            self.pool.append(conn)
    
    def close_all(self):
        """
        关闭所有连接

        程序退出时调用：逐个真正关闭，再清空列表。
        """
        for conn in self.pool:
            try:
                conn.close()
            except Exception as e:
                print(f"[ERROR] 关闭数据库连接失败: {e}")
        self.pool.clear()                  # 清空列表（即使个别连接关闭失败也清）


# 创建数据库连接池实例
# 模块级别直接实例化：import 本模块时就建好了 10 个连接（全局单例用法）
db_pool = DatabasePool(DATABASE_NAME, pool_size=10)

```

### 小结

- **连接** = 打开的数据库会话（对 SQLite 就是一个打开的文件句柄 + 内存状态），不是表，也不是进程
- **连接池** = 连接的缓存，借/还代替建/关；限制的是并发数据库操作数而非用户数
- 本项目（SQLite + Flask 单机）朴素模式足够，实际 8 处引用全部使用 db.py；db_pool.py 是备用练习实现，尚未接入任何模块
- 面试考点：为什么用连接池？——复用昂贵的建连开销，避免频繁建立/断开的性能浪费，同时限制总连接数

### 4.2 CLI vs GUI

- 底层能力相同；CLI 快、可写脚本自动化、能被其他程序调用；GUI 直观、适合浏览查看
- 命名规律："xxx CLI" = xxx 的命令行版

### 4.3 Node.js（部分插件 CLI 的依赖）

- **让 JavaScript 脱离浏览器直接在操作系统上运行**的运行时，相当于 JavaScript 的"python.exe"
- `npm` 是它的包管理器（对应 Python 的 pip/uv）
- 前端开发（Vue/React）必需；很多编辑器插件的后台进程也是 Node 写的，报 `Node.js was not found on PATH` 即缺它
- 安装：`winget install OpenJS.NodeJS.LTS`

### 4.5 WAL 模式与配套文件（-wal / -shm）

之前说“长期方案是开 WAL，现阶段暂不动”——现在有工具替你开了：DBCode 的驱动连库时会自动执行 `journal_mode=WAL`，以 WAL 模式打开库。此时库文件旁会出现两个配套文件：

| 文件 | 作用 |
|---|---|
| `interview_system.db-wal` | **预写日志**：新写入先追加到这里，空闲时再批量合并回主库（checkpoint 检查点），读写不再互斥 |
| `interview_system.db-shm` | **共享内存索引**：多个进程读 WAL 时用来协调 |

对比默认模式（直接写主库，只出现 `-journal` 锁文件），WAL 把“写”变成先记日志，别人读主库不受影响——正是之前撞锁问题的官方解法。

**什么时候出现 / 消失**

- 出现：任何程序第一次以 WAL 模式打开库的瞬间。WAL 是持久设置（写进库文件头部），之后每次打开都伴随这两个文件
- 消失：最后一个连接正常关闭时，SQLite 会自动把 WAL 合并回主库并删除这两个文件。还能看到它们 = DBCode 还连着（或上次没干净关闭）
