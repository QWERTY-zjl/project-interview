**关键机制（为什么改动这么少）**：`submit_text_answer` 查下一题用
`WHERE interview_id=? AND id > 当前题id ORDER BY id ASC LIMIT 1`。
提交时插入追问题（自增 id 必然更大）→ 它自动成为"下一题"返回前端。
所以取题接口、前端答题流程、面试状态流转全部零改动。

**进度条口径（已确认）**：前端 `progressPercentage = (currentQuestionIndex + 1) / totalQuestions`，
`totalQuestions` 来自 info 接口的 `interviews.question_count`。因此插追问题时顺手
`question_count + 1`，分母同步变大，进度条自动一致，前端零改动。

**次数与成本（已定稿）**：每题最多追问 1 次（追问题不再触发决策），每场最多 3 次
（COUNT 硬闸）；每次提交答案多 1 次 qwen-flash 决策调用（输入约 1000 token、输出约
100 token，单次成本厘级），主流程延迟增加 1~3 秒。

## 1. 新建 `app/ai_services/followup_service.py`

整文件复制以下内容（注释解释了每段语法的作用，可对照学习）：

```python
"""
追问决策智能体（followup_service）
====================================
职责单一：观察候选人刚提交的回答，自主决定「追问」还是「放行」。

设计原则：智能体只做决策，不写数据库——INSERT 由调用方（interview_api.py）
执行。好处有两个：
1. 本模块可以单独测试（决策对不对，跟写库成功与否解耦）
2. 失败兜底简单：任何异常都返回 None（= 放行），绝不会卡死面试主流程

智能体三要素的体现（答辩口径）：
- 自主决策：followup / next 的分支由 LLM 输出的 JSON 决定，不是代码写死的 if
- 感知上下文：题目、回答全文、面试类型、已问列表，全部实时查库获得
- 使用工具：查题、查回答、统计追问次数——都是进程内 SQL 函数调用
"""

import logging

# LLM_MODEL：出题/报告/提示共用的文本模型（qwen-flash），追问决策复用同一个模型
from app.config.config import LLM_MODEL
# call_llm_api：question_service 里现成的 LLM 调用函数。
# 注意它的返回值已经是解析好的 dict（内部自带 JSON 兜底解析 _parse_json_content），
# 失败返回 None——所以本模块不需要再写 JSON 解析代码
from app.ai_services.question_service import call_llm_api

logger = logging.getLogger(__name__)

# ---------- 代码硬闸参数（在 LLM 调用之前生效：省调用费 + 防死循环） ----------
MAX_FOLLOWUPS_PER_INTERVIEW = 3   # 每场面试最多追问 3 次
MAX_TOKENS_DECISION = 300         # 决策输出就是一小段 JSON，300 token 足够，省成本


def decide_followup(conn, interview_id, question_id, answer_text):
    """追问决策智能体主函数

    参数:
        conn         数据库连接（调用方持有，本函数只读、不写、不 commit）
        interview_id 面试 id
        question_id  刚被回答的题目 id
        answer_text  候选人刚提交的回答全文

    返回:
        None  → 放行（回答不需要追问，或任何环节失败走兜底）
        dict  → {"question": 追问文本, "score_standard": 追问的评分标准}
                注意：只返回决策结果，写库由调用方负责（职责分离）
    """
    try:
        cur = conn.cursor()

        # ========== 第一道硬闸：当前题本身是追问题 → 不再追问（每题最多 1 次） ==========
        # f-string 里不用加过滤条件，直接按主键查，最多一行
        cur.execute(
            'SELECT question, question_type FROM interview_questions WHERE id = %s',
            (question_id,)
        )
        question_row = cur.fetchone()
        # 题目查不到（理论上不会发生）→ 放行兜底，不抛异常
        if not question_row:
            return None
        # question_type == 'followup' 说明这题就是上一轮追问插进来的，
        # 对追问的回答一律放行——否则会无限追问下去
        if question_row['question_type'] == 'followup':
            return None

        # ========== 第二道硬闸：本场追问总数 >= 3 → 放行 ==========
        # COUNT(*) AS n：给聚合结果起列名 n，下面按 row['n'] 取值
        cur.execute(
            "SELECT COUNT(*) AS n FROM interview_questions "
            "WHERE interview_id = %s AND question_type = 'followup'",
            (interview_id,)
        )
        if cur.fetchone()['n'] >= MAX_FOLLOWUPS_PER_INTERVIEW:
            return None

        # ========== 感知上下文：拼装智能体决策所需的全部信息（进程内"工具"） ==========
        # 面试类型名（JOIN 字典表），让追问的语气贴合"技术面/HR面"等场景
        # JOIN：interviews 表存的是 interview_type_id，类型名字典在 interview_types 表
        cur.execute(
            'SELECT t.name AS type_name '
            'FROM interviews i JOIN interview_types t ON i.interview_type_id = t.id '
            'WHERE i.id = %s',
            (interview_id,)
        )
        type_row = cur.fetchone()
        type_name = type_row['type_name'] if type_row else '通用面试'

        # 本场已问过的题目文本（防追问重复话题；含追问题本身，LIMIT 20 防爆上下文）
        cur.execute(
            'SELECT question FROM interview_questions '
            'WHERE interview_id = %s ORDER BY id ASC LIMIT 20',
            (interview_id,)
        )
        # 列表推导式：把 Row 列表拉平成纯文本列表，join 后直接可拼进 prompt
        asked = [r['question'] for r in cur.fetchall()]

        # ========== 调用 LLM 做决策（一次调用，qwen-flash，约 1~3 秒） ==========
        # system 消息定角色和输出格式；user 消息给全部上下文与决策规则
        system_prompt = (
            "你是一名经验丰富的面试官，正在评估候选人刚提交的回答，决定是否需要追问。"
            "严格输出 JSON，不要输出任何其他内容。"
        )
        # f-string 里写 JSON 样例，花括号必须双写 {{ }} 转义，否则被当成变量名报错
        user_prompt = f"""【面试类型】{type_name}
【当前题目】{question_row['question']}
【候选人回答】{answer_text[:1500]}
【本场已问过的问题】{'；'.join(asked)}

决策规则（按优先级判断）：
1. 回答含糊、缺少具体细节（例如只说"做了优化"却没说怎么做的）→ 追问，挖具体做法或数据
2. 回答与题目明显跑偏 → 追问拉回主题
3. 回答自相矛盾或真实性存疑（项目细节说不清、数据夸大）→ 追问验证
4. 回答完整、具体、切题 → 放行
5. 如果候选人回答的对象本身已是追问，一律放行（正常情况下代码硬闸已拦截）

追问要求：只有一个问题；口语化自然，像真人面试官；不超过 60 字；不得与已问问题重复。

严格输出 JSON：
需要追问：{{"action": "followup", "text": "追问内容", "score_standard": "这条追问考察什么、好的回答长什么样（50字内）"}}
放行：{{"action": "next"}}"""

        # temperature 由 call_llm_api 内部固定 0.7（追问文本需要多样性，可接受）
        decision = call_llm_api(
            [
                {"role": "system", "content": system_prompt},
                {"role": "user", "content": user_prompt},
            ],
            max_tokens=MAX_TOKENS_DECISION,
        )

        # ========== 解析决策结果（三层兜底，全部收敛到"放行"） ==========
        # 1) 调用失败/解析失败 → call_llm_api 返回 None → 放行
        # 2) action 不是 followup → 放行
        # 3) 追问文本为空 → 放行（防止插进一条空题）
        if not decision or decision.get("action") != "followup":
            return None
        text = (decision.get("text") or "").strip()
        if not text:
            return None
        return {
            "question": text,
            # 评分标准缺省值：模型没给也能入库（NOT NULL 场景不炸）
            "score_standard": (decision.get("score_standard") or "考察回答的真实性与深度").strip(),
        }

    except Exception as e:
        # 总兜底：网络断了、表结构变了、任何意外——都当作"放行"处理，
        # 记日志方便排查，但绝不向上抛异常拖垮提交流程
        logger.error(f"[Followup] 决策失败（放行兜底）: {e}")
        return None
```

### 改动 2：核心接线（原 L254-264 区域）

原代码顺序是 `UPDATE 回答 → SELECT 下一题 → commit`。
改成 `UPDATE 回答 → commit → 决策+插追问 → SELECT 下一题`：

```python
        # （UPDATE 回答的原 248-252 行代码不动）

        # ★ 原来的 conn.commit() 从"查下一题之后"上移到这里：
        # 回答先落盘，后面追问决策/入库即使全部失败，答案也不会丢
        conn.commit()

        # ★【追问智能体】观察回答，自主决定是否插入追问题
        try:
            decision = decide_followup(conn, interview['id'], question_id, answer_text)
        except Exception as e:
            logger.error(f"[Followup] 决策异常（放行兜底）: {e}")
            decision = None

        if decision:
            try:
                # 追问题语音预生成（与出题链路同款）：失败只影响预生成，不阻断入库，
                # 前端拿不到预生成音频会走浏览器 TTS 兜底
                audio_data, _ = synthesize_speech(decision["question"], interview['voice_type'])
                cur = conn.cursor()
                cur.execute('''
                    INSERT INTO interview_questions
                    (interview_id, question, score_standard, question_type, question_audio, voice_type)
                    VALUES (%s, %s, %s, 'followup', %s, %s)
                ''', (interview['id'], decision["question"],
                      decision["score_standard"], audio_data, interview['voice_type']))
                # 进度条分母同步 +1（前端 progressPercentage 分母就是 question_count）
                cur.execute(
                    'UPDATE interviews
                     SET question_count = question_count + 1 WHERE id = %s',
                    (interview['id'],)
                )
                conn.commit()
                logger.info(f"[Followup] 面试{interview['id']} 插入追问: {decision['question'][:30]}")
            except Exception as e:
                # 入库失败 → 回滚本段，放行走原流程（回答已 commit，不受影响）
                conn.rollback()
                logger.error(f"[Followup] 追问入库失败（放行兜底）: {e}")

        # （原"SELECT 下一题"的 255-261 行代码不动、位置不变——
        #   追问题 id 更大，自然被这条查询取到返回给前端）
```

注意：原来 `SELECT 下一题` 之后、`return_db(conn)` 之前的那个旧 `conn.commit()` 已上移，删掉别留两个。

## 已知边界（答辩可能被问）

- 决策延迟 1~3 秒挂在提交接口上（前端有 loading，可接受）；优化方向是把决策挪到异步任务
- 追问让实际题数与"计划题数"动态偏离——已用 question_count+1 保持进度一致
- temperature 固定 0.7（复用 call_llm_api 未暴露该参数），追问文本稳定性够用；要更稳可在 call_llm_api 加 temperature 参数透传
