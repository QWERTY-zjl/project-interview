# 知识库与考点题库方案

> 本文档记录本项目引入「岗位面试知识库」的完整方案：概念、数据来源、条目格式、检索注入方式与实施步骤。
> 对应比赛要求：作品提交说明 PPT 第二部分「数据收集与处理」中的 **知识库内容（1-2 页）** 与 **预处理与利用流程图（1-2 页）**。

---

## 1. 知识库是什么（RAG 通俗解释）

**知识库（Knowledge Base）**：一份结构化存放的领域资料，程序可以按需从中"查"出相关内容。

**RAG（Retrieval-Augmented Generation，检索增强生成）**：让大模型回答问题前，先去知识库里**检索**（Retrieval）相关资料，把检索结果**拼进提示词**（Augmented），再让模型**生成**（Generation）答案。

一句话对比：

```
不用 RAG：  简历 + 岗位  ──────────────→  LLM 凭记忆编题
用上 RAG：  简历 + 岗位 + 检索到的考点  ──→  LLM 参考真实考点出题
```

LLM 自己的知识有两个毛病：**可能过时**、**可能编造（幻觉）**。知识库相当于开卷考试的参考资料——答案以资料为准，模型只负责组织语言。

**向量库 vs 关键词检索**：

| 方式 | 原理 | 依赖 | 适用场景 |
| --- | --- | --- | --- |
| 向量检索 | 文本转成向量，按语义相似度找近邻 | 需要 Embedding 模型 + 向量数据库（Milvus 等） | 知识量大、说法五花八门 |
| 关键词检索 | 按岗位/技能标签直接过滤、匹配 | 无新依赖，Python 内置即可 | 知识条目少且已打好标签 |

本项目考点条目**自带结构化标签**（岗位、关键词）。检索方案经历两次演进：

1. **初版（已存档见 5.1）**：关键词检索，纯 JSON + Python 标准库，零依赖；
2. **当前版**：**pgvector 向量检索**（PostgreSQL 装 pgvector 扩展，向量入库、检索一条 SQL `ORDER BY embedding <=> 查询向量`）——复用项目已有的 PG 16，不引入 Milvus 等独立向量库服务；关键词检索保留为降级保底（SQLite 回退模式/向量化失败时自动切换，主流程永不阻断）。

向量检索的语义匹配能力（"锁的坑"也能对上"线程安全与锁"）与「真向量数据库」的技术展示价值是升级主因；20 条量级下 pgvector 性能余量极大，条目涨到数万也够用。

## 3. 知识条目格式设计

首批范围：**Python 后端 × 20 条**。统一存为 `app/knowledge/python_backend.json`。

单条格式（每个字段都有注释解释）：

```json
{
  "id": "py-001",
  "position": "python_backend",
  "topic": "GIL 全局解释器锁",
  "keywords": ["python", "并发", "多线程"],
  "difficulty": "medium",
  "core_question": "什么是 GIL？它对多线程程序有什么影响？",
  "answer_points": [
    "GIL 保证同一时刻仅一个线程执行 Python 字节码",
    "CPU 密集型任务多线程无法并行加速",
    "IO 密集型任务影响较小，可用多进程绕开"
  ],
  "followup_hint": "回答未提多进程/协程替代方案时追问",
  "source": "interview_python + Python 官方文档"
}
```

字段说明：

| 字段 | 类型 | 作用 |
| --- | --- | --- |
| `id` | string | 唯一编号，方便引用与去重 |
| `position` | string | 所属岗位，检索的第一层过滤条件 |
| `topic` | string | 知识点名称，供报告引用 |
| `keywords` | list | 检索关键词，与简历技能、岗位方向匹配 |
| `difficulty` | string | 难度（easy/medium/hard），出题时按面试轮次调节 |
| `core_question` | string | 核心问题，出题的"题根" |
| `answer_points` | list | 标准答案要点，供评分对照 |
| `followup_hint` | string | 追问提示，供追问智能体参考 |
| `source` | string | 出处标注，答辩时可证明非编造 |

**一份题库喂三个智能体**：`core_question` → 出题；`answer_points` → 评分报告；`followup_hint` → 追问决策。

## 4. 预处理流程（PPT 流程图素材）

```
原始资料（八股文网页 / 官方文档段落 / 面经题目）
        │
        ▼  LLM 结构化抽取（qwen-flash + 固定提示词模板）
抽取草稿（JSON 条目）
        │
        ▼  人工校对（核对答案要点，防幻觉）
        ▼
入库：app/knowledge/*.json（随代码进 git，天然版本管理）
        │
        ▼  运行时：关键词检索 → 命中条目拼入各智能体 Prompt
```

### 4.1 LLM 抽取提示词模板（批量生产条目用）

把任意一段八股文/文档粘贴到 `material` 处即可批量产出条目：

```
你是面试题库整理员。请从下面的资料中抽取 1-3 个技术考点，
严格按以下 JSON 数组格式输出，不要输出任何其他文字：
[{
  "topic": "知识点名称",
  "keywords": ["3-5个检索关键词"],
  "difficulty": "easy|medium|hard",
  "core_question": "面试官会怎么问这个考点",
  "answer_points": ["3-5条标准答案要点，每条一句话"],
  "followup_hint": "回答缺失什么内容时值得追问"
}]

资料：
{material}
```

要点：**约束只输出 JSON**（与项目现有 OpenAI 兼容接口 JSON 输出约束的用法一致）；id/position/source 由脚本统一补写，不交给模型，减少出错面。

### 4.2 人工质检环节

- 每条 `answer_points` 与官方文档核对一遍表述；
- `followup_hint` 必须是"可判断的条件"，不能是模糊描述；
- 校对通过后才合入 JSON 文件——此环节写入 PPT 即「数据质量控制措施」。

## 5. 检索与注入方式

### 5.1 检索逻辑（`app/ai_services/knowledge_service.py`）

> **【演进记录】** 下面是初版关键词检索的代码示例（现仍作为降级保底路径保留在
> search_kb 中）。当前主路径已升级为 pgvector 向量检索：
> - 入库：`app/knowledge/build_embeddings.py` 调百炼 text-embedding 模型把条目
>   向量化，写入 PG 表 `kb_embeddings`（id / kb_name / embedding VECTOR(1024)），
>   全量重建策略防条目与向量脱节；
> - 检索：`search_kb_vector()` 查询文本向量化后执行
>   `SELECT id FROM kb_embeddings WHERE kb_name=%s AND embedding <=> %s::vector < 0.7
>   ORDER BY embedding <=> %s::vector LIMIT 3`（<=> 为余弦距离，越小越相关），
>   库内选出 id 后映射回 JSON 条目；
> - 降级链：pgvector 不可用（SQLite 回退/表未建/向量化失败）→ 关键词检索
>   （下方示例）→ 零命中回退通用考点前 3 条。

```python
import json
from pathlib import Path

# Path(__file__) 是当前文件路径；parents[1] 回到 app/ 目录
# 即知识库文件固定放在 app/knowledge/ 下，与代码同仓库管理
KB_DIR = Path(__file__).resolve().parents[1] / "knowledge"


def load_kb(position: str) -> list[dict]:
    """加载指定岗位的知识库条目。

    文件名约定为 {position}.json，例如 python_backend.json。
    文件不存在时返回空列表——调用方按"没有检索结果"处理，主流程不中断。
    """
    kb_file = KB_DIR / f"{position}.json"
    if not kb_file.exists():
        return []
    # encoding="utf-8" 必须显式指定，Windows 默认编码是 GBK，中文会乱码
    with open(kb_file, "r", encoding="utf-8") as f:
        return json.load(f)


def search_kb(entries: list[dict], text: str, top_k: int = 3) -> list[dict]:
    """按关键词命中数打分，返回最相关的 top_k 条。

    打分规则很朴素：条目的 keywords/topic 在文本中每命中一次就 +1 分。
    简历技能栈越长，命中的关键词越多，得分越高——足够本项目的量级使用。
    """
    scored = []
    for entry in entries:
        # 需要匹配的词 = 关键词列表 + 知识点名，全部拼在一起检查
        terms = entry.get("keywords", []) + [entry.get("topic", "")]
        # sum(...) 对每个词数一遍命中次数后求和，就是这条目的得分
        score = sum(1 for term in terms if term and term.lower() in text.lower())
        if score > 0:
            scored.append((score, entry))
    # 按得分从高到低排序（key=lambda 是"按元组第一项排序"的惯用写法）
    scored.sort(key=lambda pair: pair[0], reverse=True)
    return [entry for _, entry in scored[:top_k]]
```

设计原则：**检索失败静默降级**——知识库缺失或无命中时返回空列表，出题智能体按原逻辑工作，主流程永不因知识库阻断（与追问智能体「决策失败默认放行」同一思路）。

### 5.2 出题注入（改造 `question_service.py`）

```python
# 在组装出题 prompt 前，先检索相关考点
entries = load_kb(position)                          # 岗位维度加载
hits = search_kb(entries, f"{position} {skills_text}")  # 用岗位+简历技能做查询
kb_block = "\n".join(
    f"- {e['topic']}：{e['core_question']}" for e in hits
) or "（无命中，正常自由出题）"

# prompt 中新增一段（细节见 prompt.py 的模板组织）
# 「以下是该岗位的真实高频考点，请优先围绕简历技能与这些考点的交集出题，
#   不要照抄原题，可变换问法与考察角度：{kb_block}」
```

注入的是**考点与问法参考**而非原文，避免生成的题目雷同。

### 5.3 后续两个注入点（首批做完再接）

- **评分报告**（`report_service.py`）：题目生成时把对应条目的 `answer_points` 存进题目记录；报告生成时取出拼入 prompt，要求逐条对照给分，评分从"凭感觉"变成"对照要点"。
- **追问决策**（`followup_service.py`）：把 `followup_hint` 一并传入追问决策的 prompt，作为"是否追问"的参考依据之一。

## 7. 与现有架构约定的关系

- **依赖最小**：向量检索复用项目已有的 PostgreSQL（pgvector/pgvector:pg16 镜像内置扩展），Python 侧零新增 pip 依赖（向量以文本字面量 %s::vector 传入）；
- **职责分离**：`knowledge_service.py` 只负责"加载与检索"，怎么用检索结果由各智能体服务自己决定（与追问智能体"只返回决策、写入由 API 层做"同构）；
- **静默降级**：知识库是增强项不是必需项，任何异常都不阻断面试主流程；
- **README 同步**：接入后需在 README 的项目结构与 AI 模型说明中补充 knowledge 目录与检索逻辑（按既定文档同步约定执行）。
