# 网络学习笔记：Client/Server / IP / 端口 / 监听 / NAT / 公网部署

> 网络主题参考笔记，涵盖 C/S 模型、IP 与端口、监听地址、一次请求的完整旅程、内外网划分与公网部署方案

## 一、Client 与 Server：一问一答的模型

### 1.1 角色定义

| 角色 | 是什么 | 项目里的对应 |
|---|---|---|
| **Server（服务器）** | 一个守在端口等请求、处理请求、返回响应的程序 | `python -m app.main` 启动的 FastAPI 进程（uvicorn 托管） |
| **Client（客户端）** | 主动发请求、接收并展示响应的程序 | 浏览器（Chrome）；curl、手机 App 也算 |

核心规则：**永远是 Client 主动发起请求，Server 被动等待并响应**。服务器不会主动找浏览器；浏览器不点按钮就没有请求。

### 1.2 一次「打开页面 → 登录」的完整数据流

```
① 双击 start_server.bat
   → 启动 Python 进程，监听 0.0.0.0:10009，开始守门等待

② 浏览器访问 http://127.0.0.1:10009/static/login.html
   → 服务器从静态文件区把 login.html 原样发回
   → 日志出现：GET /static/login.html 200
   → 浏览器渲染页面、执行页面里的 Vue 代码        （此时浏览器 = client）

③ 输入账号密码，点「登录」
   → 页面里的 JS 用 fetch 发 POST /api/auth/login（JSON 请求体）
   → 服务器路由匹配到 app/api/auth_api.py 的接口函数 → 查 SQLite、核对密码

④ 服务器返回 JSON 响应 {"status": "success", ...}
   → JS 拿到结果，弹提示 / 跳转页面
```

### 1.3 前端 / 后端 / 数据库的分工（都归同一个 10009 进程管）

| 目录 | 身份 | 在哪执行 |
|---|---|---|
| `app/static/` | 前端（发给浏览器看的页面） | 浏览器里 |
| `app/api/` | 后端（接口逻辑） | 服务器进程里 |
| `app/db/` | 数据仓库（SQLite 文件） | 服务器进程读写文件 |

## 二、IP 地址与端口

### 2.1 IP = 门牌，端口 = 房间号

- **IP 地址**：设备在网络中的门牌号，联网时自动获得
- **端口（Port）**：门牌下的房间号（0~65535）。一台电脑上可以同时跑很多服务，靠端口区分：10009 是面试系统，别的程序占别的端口
- 一个完整的「地址」= `IP:端口`，例如 `10.20.30.40:10009`

### 2.2 一台电脑同时有多个 IP

| IP | 是什么 | 会不会变 |
|---|---|---|
| `127.0.0.1` | 环回地址：「本机自己」的专用代号，每台电脑都有，不出网卡 | 永远不变 |
| `10.x.x.x` / `172.x.x.x` / `192.168.x.x` | 内网 IP：接入校园网/WiFi 后由网络分配 | 会变（DHCP 租借） |
| 公网 IP | 运营商/云厂商分配，全球唯一 | 云服务器的固定不变；家庭宽带大多不直接给 |

### 2.3 私有 IP 段（RFC 1918 全球统一规定）

这些段的 IP **永远不会出现在公网上**，专门留给内网内部使用，全世界所有内网重复使用互不冲突：

| 段 | 典型使用场景 | 例子 |
|---|---|---|
| `10.0.0.0/8` | 校园网、大型企业内网 | `10.20.30.40` |
| `172.16.0.0/12` | 中型机构内网 | `172.20.1.5` |
| `192.168.0.0/16` | 家庭 WiFi 路由器最常用 | `192.168.1.100` |
| `127.0.0.0/8` | 本机环回（自己找自己） | `127.0.0.1` |

注意：私有段不专属某个校园网/家庭，只代表「**某个内网的内部**」。

### 2.4 内外网怎么分辨（路由判断规则）

设备接入网络时除了拿到 IP，还拿到**网段范围**（子网掩码决定，如 `10.20.0.0/16` 表示 `10.20.*.*` 都算本院的）：

```
访问目标 IP 时：
├─ 目标在私有段 且 与自己同网段 → 直接院内送达（不出大门）
├─ 目标在私有段 但 不同网段     → 交给网关，可能能路由到隔壁内网
└─ 目标在公网段                 → 交给网关，穿过 NAT 一路路由到全球
```

## 三、监听（Listen）

### 3.1 监听是什么

服务器启动时必须回答「**我在哪个门牌的哪个房间等人**」——这个「门牌+房间号」就是监听地址（如 `0.0.0.0:10009`）。监听 = 在自己门口守着等请求上门，**只能监听自己电脑的 IP**（别人家的门够不着，也不用管）。

项目配置位置：`main.py` 末尾 `uvicorn.run(...)` 的 `host="0.0.0.0", port=10009`。

### 3.2 三种监听写法对比

| 监听 | 效果 | 本机 127.0.0.1 能访问？ | 局域网其他人能访问？ |
|---|---|---|---|
| `127.0.0.1` | 只开「内部专线」的门 | ✅ | ❌ |
| 单个内网 IP（如 `10.20.30.40`） | 只开这一个门牌的门 | ❌ **自己反而被拒** | ✅（但 IP 一变就失效） |
| `0.0.0.0` | **本机名下所有 IPv4 门牌全开** | ✅ | ✅ |

要点：
- `0.0.0.0` **不是「全世界所有 IP」**，是「我名下所有 IP」的通配写法，作用域永远局限本机。能不能被访问到还取决于对方在网络拓扑上找不找得到你（见第五节）
- 只监听单个内网 IP 的两个坑：① 自己用 127.0.0.1 访问被拒；② 换网络 IP 变了服务就失明
- **单 IP 监听有正当用途**：MySQL、Redis 等数据库默认只监听 `127.0.0.1`，故意只允许本机程序连，是安全措施

选择口诀：**想让别人访问 → 0.0.0.0；只想本机程序用 → 127.0.0.1**。

## 四、一次请求的完整旅程（寄信模型）

### 4.1 每个请求 = 一去一回两封信

| 概念 | 类比 |
|---|---|
| 请求（Request） | 寄信：收件人 = **对方** IP:端口，寄件人 = **自己** IP:临时口 |
| 响应（Response） | 回信：收件人 = 刚才的寄件人，寄件人 = 服务器 |
| 监听 | 在自己门口收信（Server 才需要，24 小时守门） |
| 访问者的临时口 | 浏览器临时开的收件口，收回信就关（Client 不需要监听） |

```
访问者电脑 (223.100.5.12)                     你的服务器 (10.20.30.40)
        │  请求：收件人 10.20.30.40:10009              │
        │  ──────── 寄件人 223.100.5.12:51234 ──────▶  │ ← 正在监听，收信
        │                                              │
        │  ◀──────── 收件人 223.100.5.12:51234 ──────  │
        │  响应：寄件人 10.20.30.40:10009               │
```

访问者 IP 的两个用途：① 响应数据要寄回给他；② 日志/安全统计（谁访问过你）。

### 4.2 服务器日志怎么读

```
INFO:     127.0.0.1:60001 - "GET /favicon.ico HTTP/1.1" 404 Not Found
          └── 寄件人地址（谁的信）  └─ 请求内容和路径      └─ 处理结果状态码
```

- `127.0.0.1:60001`：本机访问，60001 就是那个临时收件口
- 校园网同学访问时，这里显示他的内网 IP（如 `10.20.31.88:51789`）

## 五、校园网与公网（NAT 大院模型）

### 5.1 NAT 大院：出得去、进不来

- 校园网像一个 **NAT 大院子**：全院设备共享少数几个**公网出口 IP**，外面只能看到「院子大门」，看不到院内每台设备的门牌
- **院内 → 公网**：自由出（上网就是干这个的），所以访问公网上的云服务器毫无障碍
- **公网 → 院内某台设备**：进不来，公网请求根本路由不到你的电脑（不是监听配置问题，是网络结构决定的）
- 副作用：外面网站看到的「全校访问者」都是同一个出口 IP，无法区分到个人

### 5.2 让公网访问你电脑上服务的两条路

| 方案 | 原理 | 适合 |
|---|---|---|
| **部署到云服务器**（正式） | 租一台有固定公网 IP 的机器，项目跑在上面，安全组放行端口 | 正式上线 |
| **内网穿透**（临时） | frp/花生壳/cpolar：你主动连到公网中转服务器，它把公网流量转发回你电脑 | 给老师/同学演示 |

公网开放的安全前提：HTTPS、强密码/认证、密钥不进代码库——全世界的扫描器几分钟内就能找到暴露的服务。

## 六、IP 会变的问题与部署方案

### 6.1 为什么 IP 会变

内网 IP 由 **DHCP 协议「临时租借」**：租约到期、换教室、断网重连都可能拿到新 IP。老门牌作废，还记着旧地址的人就访问不到了。

### 6.2 三层解决方案

| 场景 | 方案 | 原理 |
|---|---|---|
| 局域网内自己用 | 设备设**固定 IP**（静态分配） | 让分配规则记住你，每次发同一个门牌 |
| 正式对外服务 | **云服务器（固定公网 IP）+ 域名** | 云服务器 IP 不变；域名是给 IP 起的固定名字 |
| IP 必变的临时对外 | **DDNS 动态域名** | IP 一变，程序自动更新域名指向 |

### 6.3 项目的部署形态

```
用户浏览器 ──访问 www.en9.cn──▶ DNS 解析 ──▶ 云服务器（固定公网 IP）
                                              ├─ nginx（443，HTTPS/SSL 终结，静态文件）
                                              └─ 转发到本机 10009 → FastAPI（docker 容器）
```

对应项目里的 `docker/` 目录（Dockerfile + docker-compose + nginx 配置 + SSL 证书）和 prd 环境配置的 `www.en9.cn`。

分层总结：**监听地址解决「开哪些门」（0.0.0.0），IP 稳定性解决「门牌会不会被换」（固定 IP + 域名）**——两个独立问题、两层方案。

## 七、报错排查速查表（实战总结）

| 现象 | 本质 | 排查方向 |
|---|---|---|
| `404 Not Found` | 敲对了门（端口通），但路径不存在 | 请求 URL 是否拼错（如双斜杠 `//api`） |
| `ERR_CONNECTION_REFUSED` | 敲的门前没人守 | 端口写对没？服务启动没？地址解析（localhost 可能解析出 IPv6 `::1`，而服务器只监听 IPv4 → 改用 `127.0.0.1`） |
| 服务器日志无请求记录 | 请求在「敲门」阶段就失败 | 前端 baseURL 配置、网络可达性 |

教训：前端接口地址用**相对路径**（`/api/...`），页面从哪打开请求就发到哪，开发/部署一套代码通用，彻底避免写死 IP 和端口。

## 八、术语速查表

| 术语 | 一句话解释 |
|---|---|
| IP 地址 | 网络门牌号；分公网（全球唯一）和私有段（内网复用） |
| 端口 | 门牌下的房间号，区分同一台电脑上的多个服务 |
| 监听 | 在自己的 IP:端口守门等请求，只能监听本机的地址 |
| `0.0.0.0` | 「本机名下所有 IPv4 地址」的通配写法，不是全世界 |
| `127.0.0.1` / localhost | 本机环回地址；localhost 是它的主机名，可能被解析成 IPv6 的 `::1` |
| DHCP | 自动「临时租借」IP 给设备的协议，租约会到期所以 IP 会变 |
| NAT | 多台内网设备共享公网出口 IP 的机制，「出得去、进不来」 |
| 网关 | 院子大门：内网设备访问外部网络的必经出口 |
| 网段/子网掩码 | 定义「哪些 IP 算同一个内网」的范围规则 |
| RFC 1918 | 划定私有 IP 段（10 / 172.16-31 / 192.168）的全球标准 |
| 域名 / DNS | 给 IP 起的固定名字 / 把域名翻译成 IP 的系统 |
| DDNS | IP 变化时自动更新域名指向的机制 |
| Request / Response | 请求 / 响应，一去一回两封「信」 |
| HTTPS / SSL | 加密的 HTTP / 加密用的证书体系 |
